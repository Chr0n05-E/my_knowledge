## 1. 先分清你在选什么：四层，别混在一起选

大多数选型失败是因为把四件独立的事当成一件：

| 层 | 你要选的是 | 换了会怎样 |
|---|---|---|
| **① 内容载体**（数据层） | 笔记以什么形式存在磁盘上：纯 Markdown 文件 / 数据库 / 私有格式 | 决定**退出成本**。这层选错，后面全都白做 |
| **② 结构约定**（结构层） | 层级怎么表达（目录？frontmatter 属性？文件名？）、关联怎么表达（双链？属性？） | 决定**你十年后还能不能在自己库里找到东西**。这层跟软件弱相关，是习惯 |
| **③ 前台**（写作层） | 你每天打字用的那个软件 | **最容易换**，也是最容易纠结的。它只影响手感 |
| **④ 视图**（呈现层） | 图谱、思维导图、目录页、发布站点、AI 问答 | **全部是可以随时重算的派生物**。不是资产 |

**如果只记一句：①②是资产，③④是耗材。** 因此评估时，把"导出能力"和"数据格式"的权重放得比"图谱好不好看"高一个量级——这也是本文第 2 节权重表的由来。

## 2. 评估维度（含建议权重，你可以改）

| # | 维度 | 建议权重 | 要看什么 / 怎么测 |
|---|---|---|---|
| 1 | **数据主权与退出成本** | ★★★★★ | 磁盘上是纯文本还是私有格式；导出是否**无损**（双链、属性、附件、历史）；导出的东西能否被别的软件直接读 |
| 2 | **结构表达力** | ★★★★★ | 层级深度是否受限；**能否一个概念挂两个父节点**（数学↔理学、CS↔数学）；是否支持属性 + 查询（自动生成目录页）；双链别名归一（`[[素数定理]]`/`[[PNT]]` 指同一节点） |
| 3 | **长期可持续性** | ★★★★☆ | 最近 6 个月是否有提交/发版；治理结构（公司/个人/社区）；**有没有改许可证的前科**（改许可、被收购 = 高危信号）；参考本年度的 Kùzu、Dendron、Reor |
| 4 | **中文支持** | ★★★★☆ | 界面语言、中文文档与社区、中文排版（标点挤压/字体）、中文搜索分词 |
| 5 | **多设备与同步** | ★★★☆☆ | 有没有手机端；同步是官方服务、自建还是 Git；冲突怎么处理；离线可用性 |
| 6 | **写作体验** | ★★★★☆ | 输入流畅度、公式（LaTeX）、表格、图片粘贴、块引用/大纲、搜索速度 |
| 7 | **视图能力** | ★★★☆☆ | 全局/局部图谱、思维导图、目录页自动生成、时间线 |
| 8 | **扩展性与可编程** | ★★★☆☆ | 插件生态；能否脚本化（CLI/API）；**能否长成你自己想要的形状** |
| 9 | **上手与迁移成本** | ★★★☆☆ | 用多久能顺手；是否需要写代码/跑服务；把现有笔记搬进去要几天 |
| 10 | **成本** | ★★☆☆☆ | 免费/订阅/一次性；自建的隐性成本（运维时间才是真的贵） |
| 11 | **检索与 AI** | ★★☆☆☆ | 全文检索质量、语义检索、本地 LLM、能否叠加第三方 RAG |

> 用法建议：先按上表把权重改成你自己的（比如你不在乎手机端就把 5 降到 ★），再去看第 4、5 节的候选——**权重不同，最优解会直接翻盘**。

## 3. 五条架构路线（先选路线，再选软件）

这一步比选软件重要：下面每条路线的**退出成本差一个数量级**。

### 路线 A：现成客户端当一体机
- **形态**：装一个软件，内容 + 结构 + 视图都在它里面。
- **代表**：Obsidian、思源笔记、TriliumNext。
- **优点**：十天可用，视图开箱即有（图谱、目录树、搜索）。
- **代价**：内容形态取决于软件（Obsidian 是纯 MD，思源是 `.sy` JSON，Trilium 是 SQLite）；结构（属性名、查询语法）会带有该软件的印记。
- **适合**：想**尽快开始写**、不打算自己写代码的人。

### 路线 B：纯文本库 + 自建视图
- **形态**：`notes/` 里全是 Markdown + frontmatter，自己（或脚本）生成图谱与思维导图。
- **代表**：本机 `E:\Knowledge` 这套骨架；Foam（VS Code）；以及任何「Markdown + 脚本」组合。
- **优点**：退出成本≈0；视图可以随便换（markmap、Cytoscape、Obsidian、Gephi 都能读）；结构完全由你定。
- **代价**：**你要维护脚本**；没有手机端；写作体验取决于你选的编辑器（VS Code 不如专用软件顺手）。
- **适合**：愿意写一点脚本、把"数据主权"和"结构自定义"排在最前面的人。

### 路线 C：大纲/属性驱动
- **形态**：以"块"和属性为一等公民，层级由 namespace/属性推导。
- **代表**：Logseq、Emacs org-roam、Tana（商业）。
- **优点**：非层级关联最自然；查询能力最强（Datalog / org-ql）。
- **代价**：**与"文件即资产"冲突**（Logseq 2.0 已转数据库；org-roam 需要你活在 Emacs 里）；层级树是二等公民。
- **适合**：思考方式本来就是"每天记一条、之后自己长出来"，而不是"先建分类树"的人。

### 路线 D：自建/发布式站点
- **形态**：笔记在文件里，另外跑一个服务或用静态生成器发布成站点。
- **代表**：Quartz、Flowershow、Wiki.js、MediaWiki + Semantic MediaWiki、Wikibase。
- **优点**：对外可读、可分享、全文检索与权限完善；语义 Wiki 的查询能力极强。
- **代价**：**要跑服务 / 维护部署**；个人单机用往往是"为了一个视图背上一台服务器"。
- **适合**：确实要给人看（数字花园、课程、团队），或者你需要 SPARQL 式的语义查询。

### 路线 E：图数据库 / 图谱引擎驱动
- **形态**：把节点和边灌进数据库（Neo4j / Oxigraph / LadybugDB），前端查询渲染。
- **代表**：Neo4j 社区版、Oxigraph、LadybugDB；LLM 抽取层 GraphRAG / Graphiti / LightRAG。
- **优点**：多跳查询、聚合提问、作为服务暴露给别的程序。
- **代价**：**多一个真相源**（笔记与库必然不一致）、常驻服务、备份与 schema 迁移、许可证坑（Neo4j 社区版 GPL-3.0、Memgraph/ArangoDB 是 source-available 非 OSI 开源）。而且本年度 **Kùzu 已归档**，正是"押注小众图库"的风险样本。
- **判断**：几百到几千条笔记**不需要**它——全量重建是秒级，"派生物永远重算"这条策略成立，而图数据库的价值前提恰恰是"全量重建太贵，必须增量维护"。
- **适合**：笔记进入数万条且日常做多跳查询；或要把图谱作为服务给 agent/网站用。

### 交叉层（不是路线，是可以后加的）
- **AI 检索层**：Khoj、AnythingLLM 等，叠加在路线 A/B 之上做自然语言提问。
- **记忆层**：Anki / FSRS 间隔重复，与叶子节点联动。
- **检索层**：全文检索（ripgrep、Obsidian 搜索）、语义检索（本地嵌入模型）。

> **组合是常态**：路线 A（Obsidian 写作）+ 路线 B（脚本生成图谱/大纲）+ 交叉层（Khoj）= 很常见且合理的配置。选型时不要以为只能选一个。

## 4. 备选清单

卡片统一格式：**许可 / 活跃度 / 存储 / 层级与图谱 / 中文 / 代价 / 什么条件下选它**。活跃度均为 2026-10-03 核实值，未核实的一律标注。

### 4.1 路线 A：现成客户端（单机软件，装完就用）

#### Obsidian ⭐ 综合最优解（若接受闭源本体）
- **许可**：闭源·免费，个人/商用/教育/政府均可（[许可页](https://obsidian.md/license)）。
- **活跃度**：v1.14.4（2026-10-01），1–3 周一个版本，稳定迭代。
- **存储**：**纯 Markdown + YAML frontmatter + 附件目录**，可被 grep/git/VS Code/pandoc 直接读。
- **层级与图谱**：任意深度文件夹树 + **属性系统**（内置 Bases，1.9 起；或社区 Dataview）可按 `parents` 字段自动生成目录页；原生全局图谱与局部图谱。
- **中文**：官方简体中文界面 + 中文论坛（forum-zh）。
- **代价**：本体闭源（但数据是纯文本，锁不住你）；官方同步/发布是付费闭源服务；常用插件有停更风险（例：**Juggl 最后一次发布 1.5.0，2022-03**）。
- **选它的条件**：你要"纯文本资产"+"尽快开始写"+"尽量不写代码"，三者同时成立。这也是我目前的默认推荐。

#### 思源笔记 SiYuan
- **许可**：AGPL-3.0（[仓库](https://github.com/siyuan-note/siyuan)）。
- **活跃度**：v3.8.7-alpha.3（2026-10-03），**当天仍有提交**，是全场最活跃的之一；安卓/iOS/鸿蒙客户端齐全。
- **存储**：`.sy`（JSON 树）+ SQLite 索引 —— **不是纯 Markdown**（支持导入导出）。
- **层级与图谱**：文档树任意深度 + 原生关系图 + 块级引用 + 属性视图/SQL 嵌入块（可自动生成目录页）。
- **中文**：原生中文产品，社区在链滴，中文资料最多。
- **代价**：私有格式，外部工具不便直读（要靠导出）；AGPL 商用需注意；插件生态小于 Obsidian。
- **选它的条件**：你把中文体验/块引用排在"纯文本资产"之前，并愿意设一个每周导出到 Markdown 的自动任务。

#### TriliumNext（Trilium Notes）
- **许可**：AGPL-3.0-only（[仓库](https://github.com/TriliumNext/Trilium)）。
- **活跃度**：v0.106.0（2026-09-25）。注意：旧仓库 `zadam/trilium` 已重定向，`TriliumNext/Notes` **已归档（2025-06-24）**——网上指向旧仓库的教程要当心。
- **存储**：SQLite 单库（可导出 MD/HTML）。
- **层级与图谱**：**数据模型天生就是树**（note 有 parent/children）——"深层级分类"这件事上原生贴合度第一；有 Note Map / Relation Map。
- **中文**：README 有简繁中文文档，Weblate 持续翻译。
- **代价**：非 Markdown 存储；同步偏自建；UI 偏工程师向。
- **选它的条件**：你确信自己主要靠"层级树"组织知识，且能接受数据库存储。

#### Logseq
- **许可**：AGPL-3.0（[仓库](https://github.com/logseq/logseq)）。
- **活跃度**：2.0.1（2026-07-13），nightly 仍在推。
- **存储**：**2.0 起从 Markdown 文件转为数据库**（这是选型关键）。
- **层级与图谱**：大纲/块引用范式，层级靠 namespace 与属性模拟，**文件夹树侧栏弱**；原生图谱在大库上表现一般。
- **中文**：官方简体中文界面情况**未核实**。
- **代价**：数据库化与"文件即资产"冲突；查询用 Datalog，门槛高。
- **选它的条件**：你的思考方式就是"每天记一条、分类后长出来"，且能接受数据库。

#### Anytype / AppFlowy（一句话级）
- **Anytype**：许可 **ASAL-1.0（非 OSI 开源**，限制商业网络），v0.57.3（2026-09-30）；加密私有对象库 + 2026 年才加树侧栏。→ 适合重视隐私/P2P，**不适合当长期资产底座**。
- **AppFlowy**：AGPL-3.0，v0.14.6（2026-10-01）；Notion 复刻，数据库视图强、**无原生图谱**（判断）。→ 做学科分类学不顺手。

#### Foam（VS Code 扩展）
- **许可**：MIT（[仓库](https://github.com/foambubble/foam)）；**活跃度**：vscode@0.46.0（2026-09-30）。
- **存储**：纯 Markdown；**层级**：靠 VS Code 资源管理器；**图谱**：有图谱面板。
- **代价**：是扩展不是应用（无移动端、无块引用、查询弱）；中文靠 VS Code 语言包。
- **选它的条件**：你想"一切都在 VS Code 里"，并接受写作体验不如专用软件。

#### 已淘汰（有明确证据）
- **Dendron**：Apache-2.0，但**最后提交 2025-06-01**（未归档，releases 为空）→ 事实停更，理念（层级即文件名）值得借鉴，**别新建**。
- **Reor**：**仓库已归档**（最后提交 2025-05-13）→ 别用。

### 4.2 路线 B：纯文本 + 自建视图（组件自己配）

这条路线没有"一个软件"，你要分别选**编辑器**、**图谱渲染器**、**思维导图渲染器**。全部组件许可都已核实。

**① 编辑器（写作用）**：任选 —— VS Code（+ Foam）、Obsidian（可只当编辑器用）、Neovim、Zettlr、甚至记事本。**关键**：文件都在 `notes/` 里，换编辑器不影响数据。

**② 图谱渲染器（自建只读查看器时）**

| 库 | 许可 | 活跃度 | 适用 |
|---|---|---|---|
| [Cytoscape.js](https://github.com/cytoscape/cytoscape.js) | MIT | v3.34.3（2026-08-25） | **首选**：`{nodes, edges}` 直接出图，自带布局与图算法 API |
| [Sigma.js](https://github.com/jacomyal/sigma.js) | MIT | 4.0 仍是 beta（2026-08-20） | WebGL，几千~十万节点最强；布局要自己配 |
| [AntV G6](https://github.com/antvis/G6) | MIT | 正式版 5.1.1（2025-06-26）后放缓 | 功能最全、中文文档最好 |
| [vis-network](https://github.com/visjs/vis-network) | Apache-2.0 | 活跃 | 上手最快，适合几百节点 |
| [d3-force](https://github.com/d3/d3-force) | ISC | 最后 push 2023-12（模块稳定，非废弃） | 只是布局算法，渲染全要自己写 |

**③ 思维导图渲染器（从大纲出图）**

| 项目 | 许可 | 活跃度 | 适用 |
|---|---|---|---|
| [markmap](https://github.com/markmap/markmap) | MIT | 仓库 2026-09-12 有提交，**正式版停在 0.18.12（2025-02）** | **Markdown 大纲直出脑图**，零转换成本（已实测可用） |
| [mind-elixir](https://github.com/SSShooter/mind-elixir-core) | MIT | 活跃（2026-10-03 仍有提交，v5.15.1） | 可交互**编辑**的脑图，官方有 exportSvg/exportPng；MD 导入非强项 |
| [Freeplane](https://github.com/freeplane/freeplane) | GPL-2.0 | 活跃（2026-09-27） | 桌面 Java 应用，节点可挂本地文件链接；MD 往返还靠第三方脚本 |
| [KityMinder](https://github.com/fex-team/kityminder) | BSD-3 | **最后提交 2019-08** | 不要用 |
| [jsMind](https://github.com/hizzgdev/jsmind) | 仓库字段 `NOASSERTION`，npm 声明 BSD-3-Clause | 低频但活着（v0.9.1，2025-12） | 嵌网页的轻量 canvas 脑图；导出为截图 |

**④ 现成的实物样例**：本机 `E:\Knowledge`（`notes/` + `tools/build.py` 生成图谱与大纲）。你可以把它当作"路线 B 到底长什么样、手感如何"的参照物，**不需要接受它**。

### 4.3 路线 C：大纲/属性驱动

- **Logseq**（见 4.1）。
- **Tana**（商业，outliner + supertags）：见 4.8——它是这条路线上唯一把"层级 + 类型化图谱 + 结构化查询"合一的工具。
- **Emacs org-roam**、**Zettlr** 等补充候选见 4.8。
- **TheBrain**（商业）："层级即图谱"的极端样本——thought 之间既有 parent-child 又有 jump link，Plex 视图天生如此，**多父归属是它的原生特性**（见 4.7、4.9）。若你的直觉是"图就是层级"，它是最贴的一个，但 Markdown 生态弱。
- 共同特征：非层级关联最强、查询最强（Datalog/org-ql/supertags），但**层级树是二等公民**，且通常与"文件即资产"有摩擦。
- **已排除**：**Roam Research**（2026 年社区仍在讨论其开发停滞 + 云端闭源 + 生态萎缩，与"长期可维护"直接冲突）。

### 4.4 路线 D：发布式 / 自建站点 / 语义 Wiki

> **本节核实程度最低**：调研时 GitHub API 被限流（403），除两条特别标注外，**许可证与最近活动均为「未核实」**，请勿把"未核实"读成"没问题"。

| 候选 | 许可 | 活跃度 | 需要常驻服务 | 层级 | 图谱 | 源文件保持纯文本 | 致命短板 |
|---|---|---|---|---|---|---|---|
| **Quartz** | 未核实（记忆 MIT） | 未核实 | **否**（静态生成器） | 部分（文件夹即路径，侧栏要自配） | **有**（graph view + 双链） | **满足**（`.md` 就是真身） | 是**发布器**不是编辑器；中文搜索分词要配置 |
| **Flowershow** | 未核实 | 未核实（在维护，推断） | **否**（可静态导出，也有托管线） | 弱 | 未核实（倾向无） | 满足 | 重心偏 AI + 托管，自建是次要路径 |
| **Wiki.js** | 未核实（记忆 AGPLv3） | 未核实 | **是**（Node + DB） | 支持（页面树） | 无原生（推断） | **不满足**（内容在库，Markdown 只是输入格式） | 单人养 Node/DB/升级/备份，运维远大于收益 |
| **Outline** | **已核实：BUSL 1.1**（由 BSD-3-Clause 变更而来） | 未核实 | **是**（Postgres/Redis/S3 兼容存储） | 支持（集合→文档树） | 无（推断） | 不满足 | **非开源许可**（BUSL）+ 自建运维重。**这是"许可变更前科"的现成案例** |
| **BookStack** | 未核实（记忆 MIT） | **已核实：v25.11.6 发布**（版本号=年月，迭代稳定） | **是**（PHP + MySQL） | **强**：书架→书→章→页，恰好贴合"大类→多级分支→叶子" | 无（推断） | 不满足（WYSIWYG + 数据库） | 定位是团队文档，**没有图谱**；单人要养 PHP/MySQL |
| **DokuWiki** | 未核实（记忆 GPLv2） | 未核实 | **是**，但最轻（PHP，**无数据库**） | 支持（`ns:sub:page` 命名空间） | 无原生（推断） | **本档最好**：页面就是磁盘上的 `.txt`，跑服务也保持纯文本 | 界面/生态偏老、无图谱、中文分词搜索弱 |
| **MinDoc** | 未核实（记忆 Apache-2.0） | 未核实 | **是**（Go + MySQL） | 支持（项目→文档树） | 无 | 不满足 | **确认是接口文档管理系统，不是脑图/图谱工具**；中文最好但单人长期价值低于运维成本 |
| **MediaWiki + Semantic MediaWiki** | 未核实（MW 为 GPLv2+） | 未核实 | **是**（PHP + DB，通常还要 ES/CirrusSearch） | 软层级（分类 + 命名空间 + 子页面拼出来） | 语义关系可查询，**无现成交互式图谱**（推断） | 不满足（Wikitext 在库里） | 为语义查询付出的模板/属性/查询语法学习曲线极陡 |
| **Wikibase** | 未核实（记忆 GPL-2.0+） | 未核实 | **是**（MediaWiki + 扩展 + 多服务） | **不支持传统层级**（条目+属性+声明，多级分支要靠属性模拟） | **本质即知识图谱**（RDF/SPARQL） | 不满足（SQL/可导出 RDF） | 对个人**严重过重**；"叶子是长篇概念阐释"正是它最不擅长的形态 |
| Dendron 式"层级即文件名"的继任者 | — | **未核实** | — | — | — | — | **没查到 2025–2026 仍在维护的同型项目**。证据不足，不给推荐 |

**判断一：这条路线什么时候值得（满足 ≥2 条）**——① 需要给别人看/发布/协作；② 真需要语义查询（"所有标了 X 且属于 Y 的概念"）；③ 已有常开机器/VPS 且愿意长期打补丁、备份、升库；④ 团队 ≥3 人。

**判断二：什么时候是自找麻烦（命中任一即放弃）**——① 只有你一人、单机、无需对外发布；② 你把"长期可维护"理解为"十年后还能直接打开这些文件"（内容进 MySQL/Postgres 就是主动制造迁移债）；③ 你还需要图谱视角（本档除 Wikibase 的 RDF 与 Quartz 的静态图谱外基本没有像样的图谱，而 Wikibase 又与"写散文式概念阐释"正面冲突）。

**判断三：唯一对单机单人划算的用法**——**把 Quartz / Flowershow 只当"发布层"**：Markdown 源文件仍由本地客户端持有（Obsidian/路线 B），只把同一批 `.md` 渲染成带层级侧栏 + 图谱的静态站。发布是**可选加装件**，停掉它笔记本体零损失；成本是一次数小时配置，而不是长期运维。反过来，把 Wiki.js / Outline / BookStack / MediaWiki / Wikibase 当**主存储** → 基本是自找麻烦。


### 4.5 路线 E：图数据库 / 语义层

| 项目 | 许可 | 活跃度 | 需要常驻服务 | 备注 |
|---|---|---|---|---|
| Neo4j（社区版） | **GPL-3.0** | 2026-09-22 有提交 | 是（JVM） | 生态最大。自用无碍，**"社区版免费"≠可随便分发组合产品** |
| Memgraph / ArangoDB | source-available（**非 OSI 开源**） | 都活跃 | 是 | 商用/托管前必须读许可原文（ArangoDB 有改许可前科） |
| **Kùzu** | MIT | **仓库已归档**：最后 push 2025-10-10，末版 v0.11.3（2025-08-21） | 否（嵌入式） | 曾是最适合个人的嵌入式图库，**现已死**（公司被收购，社区在找替代） |
| LadybugDB | 未核实 | 活跃（v0.21.2，2026-09-30） | 否 | Kùzu 的社区继任者；**自身可持续性未知**（接盘 fork 的典型风险） |
| Oxigraph | **Apache-2.0** | 活跃（v0.5.11，2026-08-30） | 可选 | RDF + SPARQL 路线，许可最友好 |

| [getzep/graphiti](https://github.com/getzep/graphiti) | Apache-2.0 | 活跃（v0.30.2，2026-09-01） | 是（要 Neo4j/FalkorDB/Neptune + LLM/embedding 端点） | **不是单机零依赖**；其时序图谱定位适合 agent 检索 |

**判断**：几百到几千条笔记**不需要**这条路线（全量重建是秒级，"派生物永远重算"成立）。它的价值前提是"全量重建太贵、必须增量维护"，你不满足。什么时候才该上：笔记进入数万条 + 日常做多跳查询、或要把图谱作为服务暴露给别的程序、或多人并发编辑。

### 4.6 交叉层：AI 检索 / 记忆 / 数学排版（可以后加，不必改变主库）

**① AI 检索/问答层（叠在已有 Markdown 库之上）**

| 工具 | 中文 | 要不要 GPU | 能否读 Markdown 库 | 关键事实 |
|---|---|---|---|---|
| **Cherry Studio** | 中文原生（官方中文文档） | 不必：嵌入可用本地小模型或 API | 支持知识库导入，Markdown 类可入库 | 开源桌面端。**中文用户最省事的叠加层**，优先试 |
| **AnythingLLM** | 有中文使用生态 | 不强制（跑本地 LLM 才吃显存） | 面向"文档摄入 + workspace"；**对本地目录的增量同步较弱**（社区有第三方同步项目） | 桌面 + 服务器双形态，功能完整 |
| **Open WebUI 的 RAG** | 有多语言界面 | 强烈建议有 | 支持按 Markdown 标题切块（保留结构），但形态是"上传文件"，**不是指向 vault 目录** | 工程成本最高（ChromaDB 多 worker 会崩、需换 pgvector/qdrant） |
| **LibreChat** | 有中文 | 不必 | RAG 能力弱（无完整内置知识库管理） | 定位是"多模型聊天前端"，不适合当主力检索层 |
| [Khoj](https://github.com/khoj-ai/khoj) | 未核实 | 不必 | 可索引 Obsidian vault | AGPL-3.0，2026-08 仍有提交；**不是编辑器**，是 RAG 层 |

**结论**：中文 + 桌面 + 低门槛 → **Cherry Studio 优先**；要跨平台多 workspace 且愿意折腾 → AnythingLLM；Open WebUI 把它当个人知识库检索层是"付出不成比例的运维代价"。还有一条更省事的路线：**留在 Obsidian 里用本地 Ollama/API 插件做检索问答**（零迁移成本，但插件维护情况未核实）。

**② 记忆层（Anki / FSRS）**：FSRS 由 open-spaced-repetition 维护并已内置进 Anki，`.apkg`/collection 可完整导出 → **无锁定风险**。两种做法：单向同步（笔记里标记 → 生成卡片进 Anki，卡上留回链，得到移动端与统计）或原地复习（Obsidian 插件，不离开 vault）。
**关键判断**：概念阐释型知识库 **90% 的内容不该进 SRS**，只把定义/公式/术语这一小撮送进 Anki。整库变复习材料是这类项目最常见的失败模式。

**③ 数学排版与层级发布**（与你的数学分支直接相关）：
- **一处更正**：Obsidian 官方数学渲染引擎**据社区插件证据是 MathJax 而非 KaTeX**（存在专门的 KaTeX↔MathJax 转义转换插件；未读到官方文档，标"高置信推断"）。语法上 `$...$` / `$$...$$` 与 LaTeX 一致，写公式本身没问题。
- **Quarto**：Pandoc 体系，`.qmd`，原生多级目录/交叉引用/参考文献，一条命令 build 出多级站点。**发布链最完整**；代价是 Markdown 方言与 vault 不完全互通、要装工具链、双链与图谱弱。
- **Jupyter Book**（现基于 MyST）：适合 notebook 驱动、要跑代码的教材；纯手写阐释用它偏重，且有 v1→v2 迁移断代风险。
- **org-mode + LaTeX 预览**：公式预览质量最高、能出多级站点；但学习成本极高、离开 Emacs 不可维护、移动端近乎不可用 → 与"本地优先 + 长期可维护 + 中文"冲突。
- **Typst**：Rust 写的现代排版系统，值得列入评估（**许可与版本本次未核实**）。
- **判断**：主库继续用 Markdown 笔记软件，**发布层与写作层分离**——要发站时用 Quarto 从某个子目录生成多级站点，不要把 org-mode 当主库。

### 4.8 补充候选（桌面/学术/自托管/加密/中文云服务）——**多数是证伪清单**

我把这一批专门查了一遍，结论比"多几个选项"更有用：**在"纯 Markdown 文件 + 手机端"这两条硬约束下，这一批没有一个同时成立。**

| 候选 | 许可 | 活跃度（2026-10-03 查） | 存储 | 层级 | 图谱 | 手机端 | 判定 |
|---|---|---|---|---|---|---|---|
| **Zettlr** | GPL-3.0 | 2026-09-22 | **纯 Markdown + frontmatter** ✅ | **扁平文件列表**，层级只能靠文件夹 | 有 Graph View（文档已核实） | **无** | **格式完美、平台不满足**：若你放弃手机端，它是路线 B 的现成前台候选 |
| **SilverBullet** | MIT | **2026-10-01（本批最活跃）** | 磁盘上纯 Markdown + Lua 插件 | **弱**：主打扁平页面 + 链接 + `${query}`，无多级树视图 | 未核实 | PWA（手机浏览器可用，非原生 App） | 自托管成本 + 层级模型与你的需求方向相反 |
| **Joplin** | AGPL-3.0 为主（条款细节未核实） | 2026-09-27 | **SQLite 数据库**，Markdown 只是导入导出格式 | 支持子笔记本多级（官方文档已核实） | 无官方图谱（未核实插件） | **全平台** ✅ | **违反"文件即笔记"**：可用，但不是文件式知识库 |

| **vimwiki** | 显示 "other"（未核实） | 2026-04-30 | 纯文本 wiki 格式（非 Markdown） | 有（列表式） | 无 | 无 | 排除 |

| **WikidPad** | — | **未核实（疑似长期停滞）** | — | — | — | — | 不推荐 |

**两条重要推断（请当作推断，不是事实）**：
1. 这一批的价值在于**证伪**：真正同时满足"纯 Markdown 文件 + 手机端"的，仍然是 Obsidian / Logseq / 思源（思源严格说不是纯 MD）/ Foam（无手机端）那一圈——也就是你已经在评估的主清单。**不要因为"想找个更小众更合适的"而绕圈。**
2. 你需要的"顶层几大类 → 多级分支 → 叶子"是**强层级**结构，而 org-roam / TiddlyWiki / SilverBullet 都是"**扁平 + 链接**"范式，**方向与你的需求相反**。纯 Markdown 阵营里最贴合强层级的做法就是**用文件夹做层级**（Obsidian / Foam / Zettlr 都行）——这一点与第 4.2、4.9 节的结论一致。



### 4.9 专项对比：你最可能被卡住的一点 —— 一个概念挂两个父节点

你的例子（数学既属理学又独立成类、计算机科学既属工程学又长在数学上）在选型时会被**大多数工具默默失败**：它们只支持"一个节点一个父节点"。这一维度值得单独打分，因为它是**结构的硬约束**，事后很难补。

| 候选 | 多父归属能力 | 依据 |
|---|---|---|
| **路线 B（纯文本 + frontmatter）** | **完全自由**：`parents: [a, b]`，树取第一个、其余画成交叉边 | 事实（本机实物样例就是这么做的） |
| **Obsidian** | **可以**：属性支持列表字段（`up: ["[[代数]]", "[[计算机科学]]"]`），Dataview/Bases 能在两个父节点页里都列出它 | 事实（属性系统支持列表）+ 判断（具体呈现需实测） |
| **Anytype / AppFlowy** | **可以**：它们的关系（relation）字段天生是多对多 | 事实（文档模型） |
| **TriliumNext** | **可以**：支持把同一笔记 clone 到多个父节点下 | **未核实**（我有印象但本次未查证，请自行确认） |
| **思源 SiYuan** | **部分**：文档树是严格单亲，多归属要靠块引用/双链 + 属性视图绕 | 判断（文档树模型事实，绕过效果需实测） |
| **Logseq / org-roam** | **部分**：一个页面只有一个名字（namespace 决定位置），多归属靠属性与双链表达，看不出"树里两处都有" | 判断 |
| **markmap / 纯大纲类** | **不能**：大纲本质是树，一个节点只能在一个位置 | 事实（树的数据结构约束） |
| **图数据库路线** | 天然支持，但你为此付出的代价远大于收益 | 事实 |

**怎么用这一栏做决定**：如果你的分类体系里"跨类归属"是常态（看你的例子，很可能是），那么**单亲工具（思源文档树、Logseq）在这一点上会持续让你别扭**，而 frontmatter 列表字段（Obsidian / 路线 B）与关系型工具（Anytype / AppFlowy）天然合适。

## 7. 试错与止损：怎么在不浪费时间的前提下选

**核心原则：先做一次"两周小试点"，然后再决定要不要迁移全部笔记。**

### 7.1 试点动作（每个候选都跑一遍，半天到两天）

| 测试 | 为什么关键 |
|---|---|
| 建 **1 个多父节点**（如"线性代数"同时挂"代数"和"计算机科学"） | 检验结构表达力——这是你需求里最容易卡住的地方 |
| 写 **1 条含 3 个公式的笔记**（行内 + 独立成行） | 数学分支的硬指标，也要测输入手感 |
| 插 **1 张本地图片** | 书法/美学分支必须有 |
| 从 5 个不同入口**搜同一个概念**（标题、别名、标签、正文、拼音） | 检索决定十年后的可用性 |
| **导出全部**，再用另一个软件打开导出的东西 | 唯一能验证"退出成本"的动作，别信宣传页 |
| 在**手机**上打开并改一个字 | 同步与冲突的真实体验 |
| 用 **git diff** 看一次改动 | 纯文本路线的最大红利：能版本化、能看清自己改了什么 |
| 删除候选 | 两周后留 1 个，其他删掉。**不删就会一直纠结** |

### 7.2 三条"无论选谁"的硬规则（防止十年后被锁死）

1. **原始内容保持纯文本**——若软件用私有格式（思源 `.sy`、Trilium SQLite），就设一个**每周自动导出到 Markdown + git** 的任务，导出目录也算资产；
2. **结构必须可导出**——层级与关联不能只活在该软件的数据库里；至少要能导出成「一行一条边」的表格或 JSON；
3. **每季度做一次"这个软件明天死掉"演练**：导出 → 换一个工具打开 → 能不能找到东西。做不到就说明你在依赖它的数据库，而不是你自己的笔记。

> 参考：本年度 Kùzu 归档、Dendron 停更、Reor 归档、Juggl 插件停在 2022——**"现在很火"不构成长期保证**，能带走的资产才是保证。

## 8. 需要你回答的问题（回答完我可以收敛到 2–3 个最终候选）

1. **数据主权**：你要求磁盘上是纯 Markdown 文件（能被 grep/其他编辑器直接读），还是可以接受软件自己的数据库格式（只要导出方便）？
2. **代码意愿**：你愿意为知识库写/维护一点脚本（Python/JS）或跑一个本地服务吗？还是希望"装完就能用，永不碰命令行"？
3. **设备**：需要手机端吗？多设备同步你倾向「官方付费同步」「自建/Git」「只在一台电脑上」哪种？
4. **量级与增长**：预计最终多少条笔记（几百 / 几千 / 上万）？增长是"每天几条"还是"集中整理"？
5. **发布**：需要对外发布（数字花园/博客/给人看的站点）吗？
6. **AI**：需要自然语言问答/语义检索吗？愿意用本地模型还是接受 API key？
7. **软件许可偏好**：只接受开源，还是"闭源但免费且本地"也可以？
8. **现有材料**：你已经有笔记/大纲/思维导图文件需要迁移吗？大概什么格式、多少量？
